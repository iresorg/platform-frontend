Known data gaps, no fix available yet

No numeric severity on casesbackend limit

The original spec wants a 0–15 number shown alongside the severity badge. The real case object only has a word (LOW/MEDIUM/HIGH/CRITICAL) — no number exists to show. Not faked.

No distinct "escalated" statusbackend limit

Escalating a case only bumps severity and sets it to INVESTIGATING — there's no separate status value. The portal's "Under review by a senior analyst" wording can't be literally triggered as a result; is_escalated is shown on the analyst side instead, where it does exist.

Cases still carry no customer identitybackend limit

Even after the latest backend update, a case row has no customer_id or customer_name — only branch_label and is_test were added. The Triage Queue's Customer column shows the analyst's own active tenant, which is accurate but not a true per-row field.

Closed today: bulk onboarding is now wired up

JSON/file customer onboarding shippeddone

The Customers list now has an Onboard customer button (admin only) that calls POST /admin/customers/onboard — previously wired on the backend but unused by this app. It supports both of the ways that endpoint takes input: upload a tenant.json file (a single customer object, or a JSON array to onboard several in one go), or enter a customer's id, name, sector, service tier and branches by hand. Creating an org via the simpler POST /tenants (name + slug only, on the Tenants screen's "Create organization" dialog) still has no file upload — that's a separate, narrower endpoint and is unaffected by this change.

Process / cleanup

  • Portal Users still shows mock data to real tenants in production — needs the same "coming soon" treatment the other mock portal screens already got.
  • Several throwaway test organizations from different rounds of testing need deleting on the backend (the frontend has no DELETE on cases/orgs to do it itself).
  • No staff/analyst-level test login exists right now — the one account available is a real tenant_admin and correctly gets 403'd on every analyst/admin route. That's meant the newest screens (Customers, the Triage Queue's customer filter) could only be verified structurally, not against real populated data. A dedicated staff test account would unblock that.
04

Active issue: wrong default organization on login

Reported this week: a staff admin logs in and the organization shown active isn't their own, until they manually switch to it.

Confirmed backend-side, not a frontend buginvestigating

Checked the raw GET /me response directly — the backend itself reports the wrong tenant as active, before the frontend touches it. The UI's org switcher reads that field directly and displays it faithfully; there's no caching or stale-read path in front of it that could be the cause.

The backend treats "active tenant" as a sticky pointer on the account, not something recalculated at login. Whichever tenant was last switched into in a previous session stays active on every future login, rather than resetting to the account's own organization. Confirmed live: switching tenants, logging out, and logging back in on a different test account correctly reset to that account's home org — so the mechanism works, it's specifically this account's stored state that's pointed at the wrong place, almost certainly left over from an earlier cross-tenant investigation.

Fix now

Switch into the correct organization once, from the org switcher. That updates the backend's stored pointer and future logins should default there.

Fix for good

Needs the backend to track an actual "home" organization per account and reset to it on every login, regardless of switch history. There's no such signal in the API today to build a frontend workaround on.

Security notes

What's been checked and where things stand on the items that matter most.

Cross-tenant data isolationre-tested, holding

The original finding — an unrelated organization's token able to read another real customer's cases, devices and metrics — no longer reproduces. Re-tested from scratch with two brand-new, mutually unrelated test organizations: direct reads of /cases, /endpoints, /metrics/overview, /alerts and /fleet/devices all came back correctly scoped and empty, not another org's data. Also checked two vectors the original finding didn't cover — switching into a tenant you're not a member of, and direct-ID access to another tenant's fleet tokens — both correctly refused.

One lower-severity item remains open: GET /dashboard/kpis/ returns an unassigned-alert count that's identical across every account tested, including a brand-new one. Looks like a shared/global queue rather than leaked customer data, but worth a direct backend confirmation rather than treating it as closed on a one-sided retest.

Role & tier enforcementnow real

Used to be a frontend-only guess with no server-side backing. The backend now returns role/tier/user_type directly on GET /me and enforces it server-side — a tenant token now gets a genuine 403 on analyst routes, confirmed live.

Branches & environment

  • main is the canonical branch — the full build (all 25 screens) plus the client-onboarding addendum. Everything in this report describes main.
  • dev is a safety snapshot taken mid-build, kept as a known-good fallback. It predates the addendum work (Customers, Accept Invite, the Triage Queue/Case Workspace/Devices changes), so it's now behind main — treat main as the one to build on.
  • Production build (next build) is clean on the full route tree. An earlier Turbopack font-resolution bug only showed up against a temporarily smaller route set during a branch experiment and hasn't recurred since the full build came back.
  • Dependencies current as of this update: Next.js 16.3.8, React 19, plus the usual security/patch bumps.
